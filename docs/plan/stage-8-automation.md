# Этап 8. Автозапуск, эксплуатация и слой управления

**Цель.**
- Дайджест появляется в `outputs/` сам каждое утро по будням, без участия человека. К моменту, когда админ или СММ нажмёт кнопку в боте, он уже готов. Сбои видны, данные защищены бэкапом.
- Все действия, которые понадобятся людям, собраны в **одном слое управления**: собрать или получить дайджест, выбрать тему, сделать пост, узнать статус, оставить замечание. Сейчас им пользуется командная строка оператора, после пилота — Telegram-бот (этап 10). Бот подключается к готовым и проверенным функциям, конвейер переделывать не придётся.

**Оценка:** 1,5 дня. **Зависит от:** этапов 6 и 7.

---

## Что выяснено о ноутбуке (02.11.2026)
- **Часовой пояс** `West Asia Standard Time` (UTC+5, совпадает с Ташкентом). Расписание задаётся в местном времени без пересчёта.
- **Прав администратора нет.** Модуль `ScheduledTasks` доступен, свои задачи видны. Значит, задачи регистрируются **от текущего пользователя** с режимом «только при входе в систему». Пароль хранить не нужно.
- **Ноутбук с батареей.** По умолчанию задачи Windows **не запускаются от батареи и останавливаются** при отключении от сети. Это нужно явно отключить.
- **Современный спящий режим** (S0 Modern Standby), гибернация доступна. Таймеры пробуждения в S0 работают ненадёжно. Главная защита — запуск пропущенной задачи при пробуждении (`StartWhenAvailable`), а не пробуждение по таймеру.
- **Telegram Bot API** (`api.telegram.org`) с ноутбука доступен (проверено 03.11.2026). Для этапа 10 сеть не помеха.
- **Риск:** на корпоративном ноутбуке групповые политики могут запретить создание задач. Проверяется первым шагом этапа.

## Слой управления — `src/uzdigest/service.py`

Один модуль с функциями, которые возвращают структурированные данные (pydantic-модели), а не печатают текст. CLI вызывает их сейчас, бот на этапе 10 будет вызывать их же. Так всё поведение, которое увидят пользователи, тестируется и обкатывается на пилоте **до** появления бота.

| Функция | Что делает | Сейчас (CLI) | После (бот, этап 10) |
|---|---|---|---|
| `get_or_build_digest(date=today, force=False)` | Если дайджест за сегодня уже собран (утренний запуск) — сразу возвращает его. Если нет — запускает сбор и сборку с блокировкой от параллельных запусков. `force` пересобирает с учётом новостей, вышедших после утра; кэш Claude экономит повторную работу | `uzdigest run [--force]` | кнопка «Собрать новости»; «Обновить дайджест» у админа |
| `run(kind)` | Сбор и/или сборка по расписанию. Результат: статус, окно, число статей, причины сбоев | `uzdigest run`, `uzdigest collect` | — (Планировщик) |
| `latest_digest(date=None)` | Пути к `digest.{ru,en,uz}.md` и `digest.json`, краткая сводка: число статей по разделам, заголовки | `uzdigest status` показывает путь | сводка и файлы в ответ на «Собрать новости» |
| `list_topics(date)` / `make_post(…)` | Темы дня для выбора и готовый пост под площадку (этап 7) | `uzdigest topics`, `uzdigest post` | выбор темы → площадки → языка → готовый пост |
| `status()` | Последний сбор и дайджест (время, итог), какие источники не отвечают, состояние Claude (лимит, токен), сколько постов сделано сегодня, когда следующий запуск по расписанию | `uzdigest status` | кнопка «Статус» у админа |
| `add_feedback(…)` / `list_feedback(…)` | Замечания к дайджесту и постам: тип (пропущено / дубль / лишнее / ошибка / перевод / пост / прочее), id статьи, текст, автор, дата | `uzdigest feedback add / list / export` (оператор на пилоте) | см. этап 10 |
| `describe(…)` | Человеческий текст статуса и ошибок на русском: «Дайджест готов в 09:41, 23 статьи. Не ответил сайт uzreport.news». Без технических терминов | вывод `uzdigest status` | ответы бота |

**Точка уведомлений.** После каждого `run` вызывается список уведомителей из `settings.yaml` (`notify: [log]`). Сейчас там только запись в лог. На этапе 10 добавится `telegram`: если утренний дайджест не собрался, админ получает сообщение с причиной. Конвейер о Telegram ничего не знает.

**Правило.** Бот не получает своих путей в БД и конфиг: всё, что он умеет, сначала появляется в `service.py` и проверяется через CLI.

## Задачи
1. **`src/uzdigest/service.py`** — функции из таблицы выше, модели результатов в том же модуле.
   - `cli.py` переводится на вызовы `service.py`, чтобы не было двух реализаций.
   - Миграция `NNN_feedback.sql`: таблица `feedback(id, created_at, digest_date, article_id, kind, text, author, source)`. Поле `source` принимает значения `cli` или `telegram`, автор на пилоте — имя, которое вводит оператор.
2. **`scripts/run.ps1` — обёртка запуска.**
   - Переходит в папку проекта и запускает `.venv\Scripts\python.exe -m uzdigest <команда>`.
   - Пишет код завершения в `logs/scheduler.log`.
3. **`scripts/install_tasks.ps1` — регистрация двух задач через `Register-ScheduledTask`.**

   | Задача | Расписание | Команда |
   |---|---|---|
   | `UzDigest-Digest` | пн–пт 09:30 | `run` = сбор + дайджест |
   | `UzDigest-Collect` | пн–пт с 08:00, каждые 2 ч, до 20:00 | `collect` |

   Настройки обеих задач:
   - `StartWhenAvailable` — выполнить при пробуждении, если время пропущено;
   - `AllowStartIfOnBatteries`, `DontStopIfGoingOnBatteries`;
   - `WakeToRun` — попытка разбудить, не гарантирована;
   - `ExecutionTimeLimit` — 1 ч;
   - `MultipleInstances = IgnoreNew`.

   Скрипт написан так, чтобы на этапе 10 в него добавилась третья задача `UzDigest-Bot` (запуск при входе в систему).
4. **`scripts/uninstall_tasks.ps1`** — удаление задач. Удаляет только задачи `UzDigest-*`.
5. **Блокировка от параллельных запусков.** Файл `data/run.lock` с PID и временем. Блокировка старше 2 ч считается зависшей. `collect` и `digest` не работают одновременно с одной БД. Если админ и СММ нажмут «Собрать новости» одновременно, второй получит понятный ответ «сбор уже идёт, пришлю, как будет готово», а не ошибку.
6. **Бэкап БД.**
   - Перед каждым `digest` выполняется `sqlite3.Connection.backup()` в `data/backup/uzdigest-ГГГГ-ММ-ДД.sqlite3`.
   - Хранятся 14 последних копий. Удаление более старых — только после ответа команды на вопрос 4 в README.
   - Удаляются **только** файлы по этому шаблону в `data/backup/`.
7. **Мониторинг.**
   - Подвал дайджеста (этап 6).
   - `uzdigest sources-check`.
   - `uzdigest status`: текст из `describe()` и флаг `--json` для машинного разбора.
8. **Инструкция оператора** `docs/operations.md` (для технического участника команды):
   - как включить и выключить автозапуск;
   - где лежат дайджесты и логи;
   - что делать, если дайджеста нет;
   - как записать замечание коллеги (`feedback add`);
   - как заменить токен Claude;
   - как добавить источник.

   Инструкция для админа и СММ появится вместе с ботом на этапе 10.

## Тесты
- `service.run`: занятая блокировка → результат «уже идёт», зависшая блокировка снимается.
- `get_or_build_digest`: дайджест есть → возвращается без запуска. Нет → запускается сбор. `force` → пересборка, повторных вызовов Claude по уже обработанным сюжетам нет.
- `service.status` и `describe`: дайджест есть / нет / с ошибками источников / Claude недоступен. Тексты сравниваются с эталонами — это будущие ответы бота.
- `feedback`: добавление, список за дату, выгрузка в CSV.
- Уведомители: после `run` вызываются по списку из настроек, сбой уведомителя не роняет `run`.

## Проверка
1. **Права.** Первым шагом пробная задача «через 2 минуты» проверяет, что политики разрешают создавать задачи. Если запрещено — запасной вариант: ярлык в автозагрузке и запуск `run` при входе, если сегодняшнего дайджеста ещё нет. Согласовать с командой.
2. **Пропущенный запуск.** Ноутбук спит в 09:30 → после пробуждения задача отрабатывает, дайджест появляется.
3. **Батарея.** Ноутбук от батареи в 09:30 → задача запускается.
4. **Два рабочих утра подряд, одно из них понедельник** — дайджест появляется сам. В понедельник окно около 72 ч.

## Готово, когда
- Все четыре проверки пройдены.
- CLI работает только через `service.py`, тесты слоя управления зелёные.
- `docs/operations.md` написан.
- Бэкапы создаются.

## Итоги реализации (03.11.2026)

Код: [service.py](../../src/uzdigest/service.py) (слой управления), [ops.py](../../src/uzdigest/ops.py) (блокировка, бэкап, уведомители), миграция [008_feedback.sql](../../src/uzdigest/db/schema/008_feedback.sql), блоки `schedule`, `backup`, `notify` в `settings.yaml`, скрипты [run.ps1](../../scripts/run.ps1), [install_tasks.ps1](../../scripts/install_tasks.ps1), [uninstall_tasks.ps1](../../scripts/uninstall_tasks.ps1), инструкция [operations.md](../operations.md). Новые команды: `status [--json]`, `feedback add / list / export`. Тесты: [test_service.py](../../tests/test_service.py).

### Решения, принятые по ходу работы
- **Через `service.py` идут команды людей и Планировщика:** `collect`, `digest`, `run`, `topics`, `post`, `status`, `feedback`. Служебные команды разработки (`sources-check`, `dedup-report`, `verify-laws`, `draft`, `llm-check`, `rerender`) остались прямыми: бот их не вызывает.
- **`service.run` не бросает исключений**, а возвращает `RunResult` со статусом `ok | partial | failed | busy | exists`: так бот и уведомители получают результат одним объектом. Код выхода CLI: 0 — готово или уже собран, 1 — частично или сбой, 3 — уже идёт другой запуск.
- **Блокировка** — `data/run.lock` (вид запуска, PID, время), общая для `collect`, `digest` и `run`; старше 2 ч — снимается. Испорченный файл блокировки оценивается по времени изменения.
- **Бэкап** — `data/backup/uzdigest-ГГГГ-ММ-ДД.sqlite3` перед каждой сборкой; повторная сборка в тот же день обновляет копию дня. `backup.keep_last: null` — старые копии не удаляются до ответа на вопрос 4; когда число задано, удаляются только файлы по этому шаблону, ручные `uzdigest-before-*` не трогаются.
- **`describe_status` и `describe_run`** — тексты будущих ответов бота, с правильными окончаниями («2 статьи», «25 статей»). Источник, который ещё ни разу не опрашивался или с ошибкой последнего опроса, — в «Не отвечают».
- **Следующий запуск** в `status` считается по блоку `schedule` в `settings.yaml`, а не по Планировщику: так работает и без задач. `install_tasks.ps1` берёт те же значения параметрами по умолчанию — менять вместе.
- **Скрипты `.ps1` сохранены в UTF-8 с BOM**: Windows PowerShell 5.1 без BOM читает их в кодировке ANSI и портит русский текст.
