# UzDigest: инструкция оператора

Для технического участника команды. Админ и СММ получат свою инструкцию вместе с Telegram-ботом (этап 10).

Все команды — из папки проекта в PowerShell. С 06.11.2026 UzDigest работает в контейнере Docker, поэтому команды `uzdigest ...` из этой инструкции выполняются так:

```powershell
docker compose exec uzdigest uzdigest status
```

Запускать их из `.venv` нельзя: появится новая пустая база. `.venv` нужен только для тестов.


## Что как устроено
- **Каждый будний день в 09:30** задача `UzDigest-Digest` собирает новости и дайджест дня (`uzdigest run`).
- **С 08:00 до 20:00 каждые 2 часа** задача `UzDigest-Collect` опрашивает ленты (`uzdigest collect`), чтобы короткие ленты не теряли новости.
- **Ноутбук спал или был выключен в 09:30** — задача выполнится после пробуждения. Окно дайджеста само захватит пропущенное (не больше 96 часов).
- **Одновременно идёт только один запуск.** Второй получает ответ «уже идёт» (файл `data/run.lock`; блокировка старше 2 часов снимается сама).

## Где что лежит
| Что | Где |
|---|---|
| Дайджесты | `outputs/ГГГГ-ММ-ДД/digest.{ru,en,uz}.md` и `digest.json` |
| Посты | `outputs/ГГГГ-ММ-ДД/posts/` |
| База | Том Docker `uzdigest-data`, внутри `/app/data/uzdigest.sqlite3`. Файла на Windows нет |
| Копии базы | `data/backup/uzdigest-ГГГГ-ММ-ДД.sqlite3` — перед каждой сборкой дайджеста. Старые не удаляются, пока не задан `backup.keep_last` в `config/settings.yaml` |
| Журнал конвейера | `logs/uzdigest.log` |
| Журнал бота | `logs/bot.log`: свой файл, иначе работающий бот мешал бы ротации журнала конвейера |
| Журнал Планировщика | `logs/scheduler.log` — время, команда, код завершения и вывод каждого запуска |

## Docker
Контейнер `uzdigest` описан в `docker-compose.yml`. Бот работает в нём постоянно и сам поднимается после сбоя. Сбор и сборку запускает Планировщик Windows: он наверстывает пропуски и будит ноутбук, а `scripts\run.ps1` выполняет команду в контейнере.

- **Жив ли:** `docker ps`, в строке `uzdigest` должно быть `Up`.
- **Перезапуск бота, например после правки кода:** `docker compose restart uzdigest`.
- **Журнал бота:** `logs\bot.log`, как и раньше.
- **Docker выключен:** ближайшая задача сама включит его и поднимет контейнер, это около минуты. Вручную: `docker compose up -d` после запуска Docker Desktop. В выходные задач нет, поэтому если Docker закрыли в пятницу вечером, бот вернётся в понедельник.
- **Окно ошибки Docker Desktop: кнопку «Reset to factory defaults» не нажимать.** Она стирает тома, а в томе лежит база. Обычная причина — файл `engine.sock` после нештатной остановки: закрыть Docker и отодвинуть папку `%LOCALAPPDATA%\docker-secrets-engine`. `run.ps1` делает это сам.
- **Новая библиотека:** версия в `docker-constraints.txt`, затем `docker compose build` и `docker compose up -d`. Правка кода и настроек сборки образа не требует: папки `src` и `config` подключены к контейнеру.
- **Посмотреть базу:** через контейнер или в копии `data\backup\uzdigest-ГГГГ-ММ-ДД.sqlite3`.
- **Откат на Windows:** прежние скрипты и база за 06.11 лежат в `_archive\before_docker\`. Базу взять свежую из `data\backup` и вернуть в `digests.dir` и `posts.path` пути Windows. Затем `docker compose stop` и `Enable-ScheduledTask UzDigest-Bot`.

## Голосовые посты
Сотрудник присылает боту голосовое, бот показывает расшифровку, человек при необходимости правит текст и выбирает площадку. Как это устроено:

1. Бот в контейнере кладёт запись в `data\voice` (папка общая с Windows).
2. Посредник `UzDigest-Voice` на Windows отдаёт её транскрибатору через канал `dictation-engine`. Из контейнера канал не виден, поэтому посредник работает вне Docker, из `.venv`.
3. Текст возвращается в ту же папку файлом `ID.txt`, сбой — файлом `ID.err` с причиной для пользователя. Исправленный человеком текст — `ID.edited.txt`, исходный остаётся.
4. Пост пишет Claude по промпту `post_voice_v1`. В базе и в `outputs\ДАТА\posts` такой пост называется `voice-ID`. Он входит в дневной лимит постов.

- **Жив ли посредник:** `Get-ScheduledTask UzDigest-Voice`, в поле `State` должно быть `Running`. Журнал: `logs\voice_bridge.log`, тексты туда не пишутся.
- **Запустить вручную:** `Start-ScheduledTask UzDigest-Voice`. Поставить заново: `powershell -NoProfile -ExecutionPolicy Bypass -File scripts\install_tasks.ps1 -VoiceOnly`.
- **Транскрибатор закрыт:** посредник сам запустит `Dictation.Engine.exe`. Приложение при старте завершает такой движок и поднимает свой, запись при этом повторится один раз.
- **Посредник выключен:** через 30 секунд бот ответит, что транскрибатор не запущен, и отменит запись. Включившись, посредник её не тронет: человеку нужно прислать голосовое ещё раз.
- **Настройки:** блок `voice` в `config\settings.yaml`. Там папка обмена и предельная длина записи, 5 минут. Другая модель или язык выбираются в самом транскрибаторе.
- **Скорость:** на этом ноутбуке запись на 18 секунд заняла 24–39 секунд. Пока идёт расшифровка, диктовка может подтормаживать: движок один.
- **Записи и тексты** остаются в `data\voice`, сами не удаляются. Папка не попадает в git и в копии базы.

## Включить и выключить автозапуск
Включить (от текущего пользователя, права администратора не нужны):

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\install_tasks.ps1
```

На новом компьютере сначала проверьте, что политики разрешают задачи: команда с `-Test` создаёт пробную задачу через 2 минуты, после неё в `logs\scheduler.log` должна появиться строка `status`.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\install_tasks.ps1 -Test
```

Выключить (удаляются только задачи `UzDigest-*`):

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\uninstall_tasks.ps1
```

Время запусков задаётся параметрами `install_tasks.ps1` (`-DigestAt 09:30` и др.) и блоком `schedule` в `config/settings.yaml`. Меняйте их вместе: по `schedule` команда `status` показывает следующий запуск.

## Как дела
```powershell
uzdigest status
```

Пример ответа: что собрано, какие источники не отвечают, работает ли Claude, сколько постов сделано сегодня, когда следующий запуск. `uzdigest status --json` — то же для машинного разбора. Подробно по источникам — `uzdigest sources-check`.

## Показатели
```powershell
uzdigest metrics
```

За 30 дней: надёжность и пропущенные утра, путь материалов от сбора до дайджеста, источники со сбоями и молчащие, запросы и токены Claude, срабатывания проверки фактов, посты и замечания коллег, что повторяется. `--days 7` — другой срок, `--json` — числа для разбора. База не меняется, лимит Claude не тратится. Короткий текст для админа — кнопка «📊 Показатели» в боте.

## Дайджеста нет
1. `uzdigest status` — идёт ли сейчас сбор и чем закончился последний.
2. Конец `logs/scheduler.log`: запускалась ли задача и с каким кодом. Коды: 0 — готово, 1 — собрано частично или сбой (подробности в выводе), 3 — уже шёл другой запуск.
3. Задачи на месте: `Get-ScheduledTask -TaskName 'UzDigest-*' | Get-ScheduledTaskInfo`.
4. Собрать вручную: `uzdigest run`. Пересобрать сегодняшний с новыми новостями: `uzdigest run --force` — уже готовые тексты Claude берутся из базы.
5. Испорчены файлы дня: `uzdigest rerender ГГГГ-ММ-ДД` — заново из базы, без сети и Claude.

## Замечания коллег
```powershell
uzdigest feedback add duplicate "Цена газа — три одинаковые темы" --article 2026-11-03-015 --author СММ
uzdigest feedback list --date 2026-11-03
uzdigest feedback export feedback.csv
```

Типы: `missed` — пропущено, `duplicate` — дубль, `extra` — лишнее, `error` — ошибка, `translation` — перевод, `post` — пост, `other` — прочее. CSV открывается в Excel (разделитель «;»).

## Заменить токен Claude
1. Под аккаунтом, чья подписка используется: `claude setup-token`.
2. Вставьте токен в `.env` в строку `CLAUDE_CODE_OAUTH_TOKEN=` (файл не пересылать и не коммитить).
3. Проверка: `uzdigest llm-check` — ответ модели и состояние лимита подписки.

## Добавить источник
1. Блок в `config/sources.yaml` по образцу соседних: код, название, вид (`rss`, `govuz_api`, `html_list`), адрес, уровень доверия A/B/C.
2. `uzdigest collect --source КОД` — пробный сбор только этого источника.
3. `uzdigest sources-check` — источник в таблице, есть материалы за сутки.
4. Отключить: `enabled: false` в его блоке.

## Telegram-бот
Инструкция для админа и СММ — [team-guide.md](team-guide.md).

- **Токен** — строка `TELEGRAM_BOT_TOKEN=` в `.env` (получить: @BotFather → `/newbot`; заменить: @BotFather → `/revoke`, затем новый токен в `.env` и перезапуск бота).
- **Пользователи** — блок `bot.users` в `config/settings.yaml`: Telegram ID, имя, роль `admin` (всё, включая «Обновить дайджест», «Статус» и сообщения о сбоях утреннего запуска) или `smm` (дайджест и посты). Остальным бот отвечает «Доступ запрещен», их ID пишутся в `logs/bot.log`. Свой ID человек узнаёт у @userinfobot. После правки списка бота нужно перезапустить.
- **Утренняя рассылка:** как только дайджест за сегодня собран (по расписанию или по кнопке), бот присылает список тем всем из `bot.users`, один раз в день. Дата рассылки и кому она доставлена — в `data/bot_state.json`: не дошло из-за сбоя сети — бот повторит сам; удалить файл — рассылка за сегодня придёт ещё раз. Человеку, который ни разу не писал боту, Telegram сообщение не доставит: в `logs/bot.log` пишется «не удалось отправить в чат…». Поэтому каждый новый пользователь сначала отправляет боту `/start`.
- **Запуск:** бот работает в контейнере, отдельной задачи нет: `UzDigest-Bot` отключена. Перезапуск, например после правки `bot.users` или кода: `docker compose restart uzdigest`. Второй экземпляр не запустится (`data/bot.lock` в томе).
- **Сообщения о сбоях:** `notify: [log, telegram]` в `settings.yaml` — админы получают сообщение, если сбор или сборка упали, Claude не обработал часть статей или остановился, в дайджесте нет статей или не ответил ни один источник.
- **Замечания из бота** («👎» под постом) — `uzdigest feedback list`, источник `telegram`.
